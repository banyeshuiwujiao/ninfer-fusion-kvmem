# 根因与修法：引擎重启竞态 —— systemd 重启撞上 VRAM 释放窗口（2026-10-15）

## 现象

`sudo systemctl restart ninfer-serve-bonsai` 后引擎连续 4 次启动失败（exit 1），
journalctl 反复出现 `Main process exited, status=1/FAILURE` + `Scheduled restart job`，
约 15 秒一次自动重试，第 5 次成功加载。期间 `/v1/models` 还出现过一次"看似就绪"的 200。

## 根因

`launch-*.sh` 直接 `exec` 构建目录二进制（`build-linux-089/apps/ninfer-serve`）。
`systemctl restart` 的时序是：向旧进程发 SIGTERM → **立即**拉起新进程。
旧进程归还 ~15.4 GiB VRAM 不是瞬时的（CUDA context 销毁 + 驱动回收有秒级窗口），
新进程跑到 CUDA 初始化时旧显存还没还完 → 分配失败 exit 1 → systemd Restart= 再拉起，
直到旧显存完全释放才成功。

## 判别方法

- `journalctl -u ninfer-serve-*.service --since "-5min"`：连续多条
  `Main process exited, status=1/FAILURE` + `Scheduled restart job` 即为本症；
- `nvidia-smi --query-gpu=memory.used`：数值逐步下降说明旧进程正在释放；
  降到基线后新进程才可能成功；
- **不要被 `/v1/models` 的 200 骗到**：那可能是旧进程尚存（或半死）时的响应。

## 修法（运维约定）

1. 重启后**先确认再动下一步**：`watch nvidia-smi` 直到 VRAM 归零/回落基线，
   再确认 unit `active` 且 models 接口 200；
2. 需要确定性时用 `stop` → 等 VRAM 释放 → `start`，而不是一把 `restart`；
3. 可选加固（未实施）：unit 加 `ExecStartPre=` 轮询 VRAM 释放，
   或调大 `RestartSec` 让重试间隔覆盖释放窗口；
4. 崩溃循环期间 guard/dsh 的连接拒绝是预期行为，不要误判成隧道故障
   （CF 530/error 1033 才是隧道问题，502 才是隧道通但本地服务不通）。

## 关联

- 2026-10-15 特性①上线实测（`absorb/018-client-compat` → `engine-dev` 8cd4890）：
  特性①为纯 serve 层协议改动，与新二进制本身无关；换任何二进制重启都会踩此窗口。
