# kvmem 0.18 更新吸收可行性评估

> 2026-10-15 · 基于 GitHub kvmem/kvmem v0.18.0 与服务器 `~/ninfer-fusion-kvmem/src-tree/fusion-engine-src` 的 git 级实测分析

## 结论（先行）

**不能做 git 级合并，但可以做特性级吸收，且有明确的高价值清单。**

核心原因：**两棵代码树不同源**。

| | 上游 kvmem 0.18 | 你的 fusion 引擎 |
|---|---|---|
| 代码树 | `kvmem/`（共享层）+ `src/adapter/`（llama.cpp 适配）+ `backends/{llamacpp,ninfer}` | NInfer 源码树：`src/{core,ops,runtime,serve,models,media,text…}` |
| 关系 | kvmem 框架 + 双后端子模块 + 集成补丁 | NInfer 引擎 + 自研 `src/ops/kvmem/`（26 个文件：score/select/retrieve/window/shadow/harvest…） |
| git 血缘 | fork 点 `44b97728`（v0.11.0 发布前） | **独立历史仓库**（不含 fork 点提交，领先 GitHub 快照，含未推送提交如 `e11b953`） |

你的 GitHub 仓库 `1314521gjy/ninfer-fusion-kvmem` 虽 fork 自 kvmem-llama.cpp，但 root 引擎文件已删（93 处 D），main 已重构成"8G 档"容器布局（`src-tree/fusion-engine-src` 快照 + 文档）。服务器上的引擎仓库是独立演进的开发主线——**merge 上游 tag 这条路从结构上就不存在**。

## 0.18 关键事实

- 0.11.0 → 0.18.0 共 **228 个提交、293 个文件变更**；跨 v0.12~v0.17 共 9 个版本
- ⚠️ 0.18 正式版**复用 RC3 二进制**，仅更新启动默认值/文档/校验和；RTX 30/40 系包**未经实机推理验证**（性能数字全部来自 RTX 5060 Ti）
- NInfer 基线 `8319e8f5` + 集成补丁

## ③ 工具调用约束（未合并，留 patch）

**移植内容**（以 `backends/patches/ninfer-kvmem.patch` post-image 为权威逐用例对齐）
- `strict_arguments` 按 schema **声明序**手拼参数 grammar（pinned xgrammar 用 map 序 `n→o→s`，与 Qwen XML 协议冲突需规避）；string 参数走 `StringConstraints` 支持 pattern。
- `normalize_json_schema` 改 `ordered_json` **保序**（普通 nlohmann::json 静默重排是排查半天的元凶）；`uniqueItems` 递归剥离（回退实现，文档化偏差）。
- required/any + 多工具**全部接受**（0.18 删 0.17 multi 拒绝）。
- forced opener 从 `to_prompt_input` 移除，约束走 `options.tool_choice`。
- `preserve_special_tokens` 删 Basic 恒真分支。

**6/6 单元全绿**（清零版 `025a322`）：`core tool constraints: PASS (grammar, strict codecs, transactional masks, three protocols)`。

**运行期 segfault（卡点）**
- 最小复现：4 工具 chat 请求 + `tool_choice:auto` + `effort:none` **必崩**；无工具请求正常。
- `addr2line` 定位崩溃点：`ninfer::ops::detail::small_t_i8::launch_tc_partial_i8`（**CUDA attention kernel host 侧**，近 NULL 读 error 4）——**非** serve 层代码，是 0.17 时代就存在的既有 bug。
- 因果链：`frontend.cpp:1231-1243`（0.18 新代码）要求 `tools_constrained` 时 `preserve_special_tokens==false` 才放行 → 默认 Basic → 进 engine grammar 约束解码路径 → 该路径踩中既有 kernel bug 崩溃。显式 `tool_constraints:"auto"`（Automatic→preserve=true）被校验拦下成 400 不崩。

**灰度折中尝试失败**：试图"默认走 0.17 自由解码、显式 `tool_constraints` 才启用 0.18 约束"，但与 0.18 语义**正面冲突**——TCT 立即断红（`Chat named choice enforced without forced prompt opener` 等）。证明没有干净的规避路径，**除非先修 kernel**。

**结论**：③ 是"不可上线"状态。已完整备份为 `~/absorb-018-tool-constraints-20261016.patch`（301 KB，7 个提交，`git am` 可恢复）。后续若要落地，主线应是修 `small_t_i8` 约束解码路径的 kernel bug（`RelWithDebInfo` 重建取源码行号 → 审查 `src/ops/softmax_attention/dense/causal_cache/small_t_i8_launch.cuh` host lambda 对空 view/零长度的假设），而非继续在 serve 层打补丁。

## 运维教训（本次踩坑）

1. **重启竞态**（已在 ① 落档）：`systemctl restart` 撞 VRAM 释放窗口会崩溃循环。约定 stop → 等 VRAM 归零 → start。
2. **重编挤爆生产引擎**：16 路并行 `ninja` + `strata` 55GB RSS 叠加打满 62GB，OOM killer 杀掉 strata（anon-rss ≈ 49GB）。**重编前应先停引擎或降并行度（`ninja -j4`）**。
3. **切分支必须重跑 cmake**：切分支后 `ninja` 链接报 `undefined reference to ninfer_bundle_entry_ninfer_openai_schema_test`——因 `build-linux-089/tests/ninfer_tests_dispatch.cpp` 是旧分支生成的注册表；需 `cmake -S . -B build-linux-089` 重新生成再 `ninja`。
